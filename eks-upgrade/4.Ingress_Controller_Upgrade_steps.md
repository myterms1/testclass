# Question: Upgrading to DST with 4.15.1 on v1.36? What is required provide everything step by step in simple straight method? includes configuration changes,  how to deploy or which module to run method, and what to test after deployment?

# Answer:
Here's the full test, step by step. Everything is in **dst (blue)** through your normal workflow.

## Step 1: Take a "before" snapshot (5 min)

So you can compare after and roll back if needed:

```bash
helm -n ingress-control list                                   # note REVISION and CHART (4.14.0)
helm -n ingress-control get values ingress-nginx -o yaml > before-values.yaml
kubectl -n ingress-control get svc ingress-nginx-controller -o wide > before-svc.txt
kubectl get ingress -A > before-ingress.txt
```

Note the NLB hostname in `EXTERNAL-IP`. It must be the **same** after the upgrade.

## Step 2: Make the config change

**File:** `gsm-metal/module/aws/eks-addons/env-config/us-east-1/dst.tfvars`
Under `params.blue.helm_charts`, add **one line** to the existing `ingress-nginx` block:

```hcl
      ingress-nginx = {
        chart_version = "4.15.1"          # <-- add this line only
        addon_config = {
          dns_record_weight = "0"         # keep whatever is already here
        }
        values = {
          # keep your existing values exactly as they are
        }
      }
```

Don't touch anything else. Kyverno's allowed registries already include `registry.k8s.io/ingress-nginx/controller:*`, so the new image will be allowed.

## Step 3: Get the change into dst

Your normal pattern: new branch → commit → PR into `dst` → merge.

## Step 4: Plan

GitHub workflow: branch **`dst`**, module **`eks-addons`**, action **plan**.

**The plan must show:**
- `module.helm_charts...chart_group_3["ingress-nginx"].helm_release.chart` **will be updated in-place**
- `version: "4.14.0" -> "4.15.1"`
- `Plan: 0 to add, 1 to change, 0 to destroy` (or only other in-place changes you expect)

**Normal and safe:** the long list of `set` lines shown as `-> null` and `(known after apply)`, like your last ingress plan.

**Stop if you see:** `must be replaced`, `destroy`, or any change to the Route53 records or the NLB.

## Step 5: Apply and watch

Run the same workflow with **apply**. In another terminal:

```bash
kubectl -n ingress-control get pods -w
```

The pods roll over one at a time. There should be no downtime, since you have at least 2 replicas.

## Step 6: Test after deployment

**1. Right version installed**
```bash
helm -n ingress-control list                    # CHART ingress-nginx-4.15.1, APP VERSION 1.15.1
kubectl -n ingress-control get pods -o jsonpath='{.items[*].spec.containers[0].image}'; echo
```

**2. Pods healthy, no errors**
```bash
kubectl -n ingress-control get pods             # all Running, no restarts
kubectl -n ingress-control logs deploy/ingress-nginx-controller --tail=100 | grep -iE "error|failed|denied"
```

**3. Service and NLB unchanged**
```bash
kubectl -n ingress-control get svc ingress-nginx-controller -o wide
```
Expect **only 443/TCP**, and the **same** NLB hostname as in `before-svc.txt`.

**4. Your metal overrides still applied**
```bash
helm -n ingress-control get values ingress-nginx | grep -E "healthcheck-port|target-group-attributes|61616|pricer"
```
Expect healthcheck port `80` and `preserve_client_ip.enabled=true`, with **no** `61616` or `pricer`.

**5. Target group: settings and health**
```bash
TG=$(aws elbv2 describe-target-groups --names k8s-ingressc-ingressn-c974591727 --query 'TargetGroups[0].TargetGroupArn' --output text)
aws elbv2 describe-target-group-attributes --target-group-arn $TG \
  --query "Attributes[?Key=='proxy_protocol_v2.enabled' || Key=='preserve_client_ip.enabled']"
aws elbv2 describe-target-health --target-group-arn $TG --query 'TargetHealthDescriptions[].TargetHealth.State'
```
Expect proxy_protocol `false`, preserve_client_ip `true`, and all targets `healthy`. Targets will show new pod IPs; that's normal.

**6. All Ingresses still have an address**
```bash
kubectl get ingress -A
```
Compare with `before-ingress.txt`: same list, ADDRESS filled in.

**7. Admission webhook accepts your Ingresses (tests the stricter rules)**
```bash
for i in $(kubectl get ingress -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}{"\n"}{end}'); do
  ns=${i%/*}; n=${i#*/}
  kubectl -n $ns get ingress $n -o yaml | kubectl apply --dry-run=server -f - >/dev/null && echo "OK  $i" || echo "FAIL $i"
done
```
Every line should say **OK**.

**8. TCS header settings active**
```bash
kubectl -n ingress-control exec deploy/ingress-nginx-controller -- nginx -T 2>/dev/null | grep -E "client_header_buffer_size|large_client_header_buffers"
```
Expect `128k` and `4 128k`.

**9. Application tests (most important)**
- Open the **metal UI** and log in.
- Open **TCS UI** and call the **TCS API**, including a request with large headers or cookies.
- Click through a few normal workflows.
- Check the app pods' logs for new errors.

## Step 7: If something is wrong, roll back

**Normal rollback:** remove the `chart_version = "4.15.1"` line (or set `"4.14.0"`), then PR → plan → apply. It's an in-place change, so the NLB stays.

**Emergency, if users are down and you can't wait for a PR:**
```bash
helm -n ingress-control history ingress-nginx
helm -n ingress-control rollback ingress-nginx <previous-revision>
```
Then still fix the tfvars, so the next Terraform run doesn't re-apply 4.15.1.

## Step 8: When dst passes

Let it run for a day or two. Then move `chart_version = "4.15.1"` from `dst.tfvars` into `eks-addons/env-config/common.tfvars` (blue and green), so every environment gets it as you promote.
