# My Question: my question is then what will i do with v1.36? if 4.15.1 is not test for v1.36?
# Answer:
On 1.36 you have no fully tested ingress-nginx option. There are three practical ways to handle that.

## Why it isn't as scary as "untested" sounds

"Tested" means the project ran its automated tests on that version. The project stopped releasing before 1.36, so 1.36 never got a run. That doesn't mean it breaks there:

- ingress-nginx uses stable Kubernetes APIs (Ingress `networking.k8s.io/v1`, Services, EndpointSlices), and 1.36 didn't remove any of those.
- The project itself states that existing deployments of Ingress NGINX will not be broken.
- **Your own dst is the proof:** 4.14.0 is running on 1.36 now and the UI works.

The real risk isn't that it suddenly stops working. It's that **there will be no more fixes**: no security patches and no fixes for future Kubernetes changes.

## Your three options

**A. Run 4.15.1 on 1.36 and test it yourself (short term).**
You become the test. Before each environment moves, check:
```bash
pluto detect-helm -A --target-versions k8s=v1.36.0
kubectl -n ingress-control logs deploy/ingress-nginx-controller --tail=100 | grep -iE "error|failed"
```
Then test the UI, TCS, certificates and NLB target health. This is fine for non-prod now.

**B. Hold prd at 1.35 until you've migrated.**
4.15.1 is officially tested on 1.35, so prd stays on a fully supported combination. Lower environments go to 1.36, and prd follows once ingress-nginx is replaced. EKS still supports 1.35, so there's no rush on the cluster side.

**C. Migrate to another ingress controller (the real fix).**
This is a separate project. Options include the AWS Load Balancer Controller (already installed, though it works differently and your NGINX-specific settings like the TCS header buffers wouldn't carry over), F5's NGINX Ingress Controller, or a Gateway API controller. There are also third-party maintained forks of ingress-nginx that continue patches. Any of these needs its own dst testing because it touches every Ingress, the NLB and DNS.

## My recommendation

- **Now:** move dst to 4.15.1, test it, and carry it through the non-prod environments on 1.36 (option A).
- **Before prd:** decide between B and C with your team. If you can't migrate before the prd window, **hold prd at 1.35** (option B). That's the only combination where every chart is officially tested.
- **Start option C** as its own project soon, since it's unavoidable either way.

This is a risk decision for your team or manager, not only a technical one. It's worth writing down which option you chose and why.
